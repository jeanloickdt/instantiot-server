1. Vue d'ensemble

Serveur IoT temps reel qui fait le lien entre des devices ESP32/ESP8266 (capteurs, actionneurs) et une app Android. Le serveur est un dumb relay — il route les trames binaires sans interpreter les payloads.

Architecture


  ESP32/ESP8266                   InstantIoT Server                      App Android
  ┌──────────┐               ┌──────────────────────┐               ┌──────────┐
  │          │──TCP:9001────▶│  DeviceRelay          │               │          │
  │  Device  │               │       │               │               │   App    │
  │          │◀──TCP:9001────│       ▼               │               │          │
  │          │               │  SessionRegistry      │               │          │
  └──────────┘               │       │       ▲       │               └──────────┘
                             │       │       │       │                    │ ▲

                             │  SQLite (WAL) │       │                    │ │
                             │               │       │                    │ │
                             │         AppRelay ◀────┼──── WS:8080 ──────┘ │
                             │               │       │                      │
                             │               └───────┼────── WS:8080 ──────┘
                             │                       │
                             │    REST API :8080     │
                             └──────────────────────┘

Flux de donnees

  • Device → App : ESP envoie trame TCP → serveur extrait widgetId + payload → met a jour RAM + history buffer → broadcast WebSocket aux apps qui regardent ce projet
  • App → Device : App envoie trame WebSocket → serveur extrait deviceIds cibles → verifie ownership → trim header → relay TCP vers les devices

Pattern architectural

Chaque module (auth, project, device, widget) suit le meme pattern :

  • domain/ — Interfaces, data classes, models serialisables (aucune dependance framework)
  • data/ — Implementation SQLite (Exposed), tables, mappers
  • *Routes.kt — Routes Ktor, validation, orchestration
Ce decoupage suit le principe Dependency Inversion (SOLID) : les routes dependent des interfaces, pas des implementations SQLite.

5. Authentification & securite

JWT

ParametreValeur
AlgorithmeHMAC256
Expiration30 jours
Issuerinstantiot-server (configurable dans application.yaml)
Audienceinstantiot-app
SubjectuserId (UUID)
Secret2x UUID concatenes, stocke dans ~/.instantiot/secret.key (chmod 600)
Securite JWT : A chaque requete authentifiee, le serveur verifie que le user existe encore en DB via userRepository.findById(). Un user supprime ne peut plus utiliser son token.

Passwords

  • Hashing : BCrypt avec salt automatique (BCrypt.gensalt())
  • Validation register : username 3-32 chars alphanumerique, password 8-128 chars
  • Admin auto-genere : 16 chars alphanumeriques via SecureRandom, affiche une seule fois dans les logs

Tokens device

  • UUID v4 genere a la creation du device
  • Retourne en clair une seule fois dans la reponse POST
  • Seul le SHA-256 est stocke en DB — le token en clair n'est jamais persiste
  • Verification a la connexion TCP : SHA-256(token_recu) == token_hash_db

Rate limiting

ScopeLimiteCleRoutes
auth10 requetes / minuteIP distante/api/login, /api/register

Ownership isolation

Chaque ressource (projet, device, widget) a un owner_id. Toutes les operations verifient :

val resource = repository.findById(id)
if (resource == null || resource.ownerId != userId) {
    respond(404, "Not found")  // ne revele pas l'existence
}

Ce pattern est applique sur :

  • Toutes les routes REST (GET, PATCH, DELETE)
  • Le handshake WebSocket (verification ownership projet)
  • Le relay per-frame (verification ownership device — in-memory, zero DB)

7. Relay temps reel — TCP & WebSocket

DeviceRelay — TCP port 9001

Fichier : relay/DeviceRelay.kt

Flow de connexion

1. ESP ouvre connexion TCP → port 9001
2. Handshake : ESP envoie [TOKEN_LEN(1B) | TOKEN_BYTES]
3. Server calcule SHA-256(token) → lookup dans DeviceTable
4. Si valide → session enregistree dans SessionRegistry, device marque online
5. ESP envoie trames binaires iWidgets v1 en continu
6. Pour chaque trame :
   a. Extraire widgetId + payload
   b. Mettre a jour lastPayloads en RAM (sub-milliseconde)
   c. Ajouter au historyBuffer (flush toutes les 5s)
   d. Update last_payload en DB (async, non-bloquant)
   e. Broadcast trame intacte aux apps qui regardent ce projet
7. Deconnexion → device marque offline, session retiree
Protections TCP :
  • Keepalive TCP active — OS detecte si le device disparait
  • Timeout 90 secondes — si rien recu, device considere offline
  • Body max 1024 bytes — frames plus grandes rejetees
  • CRC8 verifie sur chaque trame entrante

AppRelay — WebSocket /ws/app

Fichier : relay/AppRelay.kt

Flow de connexion

1. App se connecte a /ws/app avec JWT dans le header Authorization
2. JWT verifie par Ktor → userId extrait
3. Handshake : premier message texte = projectId
4. Server verifie ownership : projectRepository.findById(projectId).ownerId == userId
5. Session enregistree dans SessionRegistry avec activeProjectId
6. App envoie trames binaires (commandes vers devices)
7. Pour chaque trame :
   a. Extraire deviceIds cibles
   b. Verifier ownership de chaque device (in-memory)
   c. Trim header device de la trame
   d. Relay TCP vers les devices cibles
8. Deconnexion → session specifique retiree (multi-session supporte)
Protections WebSocket :
  • JWT requis a la connexion
  • Ownership projet verifie au handshake (DB call, une seule fois)
  • Ownership device verifie per-frame (in-memory, zero overhead DB)
  • maxFrameSize = 8 KB — frames plus grandes rejetees par Ktor
  • Ping/pong automatique (15s) + timeout (30s)

8. Protocole binaire iWidgets v1

Fichier : relay/FrameParser.kt

Format de trame

┌──────┬─────┬──────────┬─────┬───────────┬─────────────────────┬─────────────────────────────────┬──────┐
│ 0xAA │ VER │ LEN (2B) │ SEQ │ DEV_COUNT │ [DEV_LEN|DEV_ID]×N │ WID_LEN│WID│TYPE│EVENT│PAYLOAD… │ CRC8 │
│  1B  │ 1B  │  LE      │ 1B  │    1B     │    variable         │           variable              │  1B  │
└──────┴─────┴──────────┴─────┴───────────┴─────────────────────┴─────────────────────────────────┴──────┘
ChampTailleDescription
0xAA1 byteSync byte — debut de trame
VER1 byteVersion protocole (0x01)
LEN2 bytes LETaille du body (tout entre SEQ et CRC)
SEQ1 byteNumero de sequence
DEV_COUNT1 byteNombre de devices cibles (0 = device→app, N = app→devices)
DEV_LEN|DEV_IDvariableUUID device cible (repete DEV_COUNT fois)
WID_LEN|WIDvariableUUID du widget
TYPE1 byteType widget (le serveur ne l'interprete pas)
EVENT1 byteType d'evenement (le serveur ne l'interprete pas)
PAYLOADvariableDonnees opaques — stockees en base64
CRC81 byteCRC-8/SMBUS (polynome 0x07) sur le body

Directions

  • Device → Server → App : DEV_COUNT = 0. Le serveur extrait widgetId + payload, stocke, broadcast.
  • App → Server → Device : DEV_COUNT > 0 avec les UUIDs cibles. Le serveur trim le header device et relay la trame.
Le serveur est un dumb relay — il ne lit jamais TYPE, EVENT ni le contenu du PAYLOAD. Il extrait uniquement ce dont il a besoin pour router et stocker.

9. Sessions & concurrence

Fichier : relay/SessionRegistry.kt

Structures in-memory

MapTypeUsage
appSessionsConcurrentHashMap<UserId, CopyOnWriteArrayList<AppSession>>Sessions WebSocket actives (multi-device par user)
deviceSessionsConcurrentHashMap<DeviceId, DeviceSession>Sessions TCP actives
lastPayloadsConcurrentHashMap<WidgetId, String>Cache dernier payload par widget (acces sub-ms)
historyBufferConcurrentLinkedQueue<HistoryEntry>Buffer avant flush SQLite (toutes les 5s)

Multi-session

Un user peut avoir plusieurs connexions WebSocket simultanees (telephone + tablette). Chaque connexion est une AppSession independante dans la liste. Le broadcast envoie a toutes les sessions qui regardent le meme projet.

Modele de concurrence

  • 1 coroutine IO par device TCP connecte
  • 1 coroutine Ktor par WebSocket app connecte
  • 1 coroutine background pour flush history (toutes les 5s)
  • 1 coroutine background pour cleanup history > 24h (toutes les heures)
  • Toutes les structures partagees sont thread-safe (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue)

10. History buffer & flush

Device envoie trame
       │
       ▼
SessionRegistry.lastPayloads[widgetId] = payload    ← RAM, sub-ms
SessionRegistry.historyBuffer.add(entry)             ← Queue lock-free
widgetRepository.updateLastPayload(...)              ← Async IO, non-bloquant
       │
       │  (toutes les 5 secondes)
       ▼
flushHistoryBuffer()
  → drain historyBuffer
  → widgetHistoryRepository.insertBatch(rows)        ← 1 transaction SQL pour N rows
       │
       │  (toutes les heures)
       ▼
widgetHistoryRepository.deleteOlderThan(24h)         ← Cleanup automatique
       │
       │  (au shutdown)
       ▼
flushHistoryBuffer()                                 ← Flush final, zero perte
Design decision : La DB n'est jamais dans le chemin critique du relay. Le batch insert toutes les 5s est ~5x plus performant que des inserts individuels. Le cleanup 24h empeche la DB de grossir indefiniment.

13. Deploiement

Build

./gradlew shadowJar
# → build/libs/instantiot-server-0.0.1-all.jar

Lancement

java -jar instantiot-server-0.0.1-all.jar

Premier lancement

  1. Le serveur cree la DB SQLite + les tables
  2. Un compte admin est genere avec un password aleatoire
  3. Le password est affiche dans les logs — a sauvegarder immediatement
  4. Le fichier ~/.instantiot/secret.key est genere

HTTPS (recommande)

Le serveur ecoute en HTTP. Pour la production, utiliser un reverse proxy TLS devant :

# Exemple Caddy (auto-cert Let's Encrypt)
instantiot.example.com {
    reverse_proxy localhost:8080
}
Important : Le port TCP 9001 (devices) reste en clair. Documenter comme "LAN only" ou mettre derriere un tunnel/VPN si acces distant.
