1. Vue d'ensemble et architecture

Serveur IoT temps reel qui fait le lien entre des devices ESP32/ESP8266 et une app Android. Le serveur est un dumb relay — il route les trames binaires sans interpreter les payloads. Inclut un dashboard admin web integre pour la gestion du serveur.

Architecture


  ESP32/ESP8266                   InstantIoT Server                      App Android
  +-----------+               +----------------------+               +----------+
  |           |--TCP:9001---->|  DeviceRelay         |               |          |
  |  Device   |               |       |              |               |   App    |
  |           |<--TCP:9001----|       v              |               |          |
  |           |               |  SessionRegistry     |               |          |
  +-----------+               |       |       ^      |               +----------+
                              |       |       |      |                    | ^
                              |       v       |      |                    | |
                              |  SQLite (WAL) |      |                    | |
                              |               |      |                    | |
                              |         AppRelay <---+---- WS:8080 ------+ |
                              |               |      |                      |
                              |               +------+------ WS:8080 ------+
                              |                      |
                              |  REST API :8080      |
                              |  Admin Panel :8080   |
                              +----------------------+

Flux de donnees

  • Device -> App : ESP envoie trame TCP -> serveur extrait widgetId + payload -> RAM + history buffer -> broadcast WebSocket
  • App -> Device : App envoie trame WebSocket -> serveur verifie ownership -> trim header -> relay TCP vers devices
  • App reconnexion : Login -> GET layout -> GET states -> WebSocket handshake -> temps reel

Pattern architectural par module

  • domain/ — Interfaces, data classes, DTOs (zero dependance framework)
  • data/ — Implementation SQLite via Exposed, tables, mappers
  • *Routes.kt — Routes Ktor, validation, orchestration
SOLID — Dependency Inversion : les routes dependent des interfaces (ProjectRepository), pas des implementations (SqliteProjectRepository). Les repositories sont instancies une seule fois dans Application.kt comme globals.

4. Demarrage et configuration

Point d'entree

Le serveur utilise un embeddedServer custom (pas EngineMain) pour lire les ports depuis ServerConfig :

fun main(args: Array<String>) {
    ServerConfig.load()                    // ~/.instantiot/server.properties
    embeddedServer(
        Netty,
        port = ServerConfig.httpPort,      // configurable via dashboard admin
        module = Application::module
    ).start(wait = true)
}

Sequence de demarrage

1. ServerConfig.load()              <- Lire ports depuis properties
2. embeddedServer(port=httpPort)     <- Demarrer Ktor/Netty
3. install(ContentNegotiation, StatusPages, CORS, RateLimit)
4. DatabaseFactory.init()            <- SQLite WAL + tables + index
4b. deviceRepository.markAllOffline()  <- Reset isOnline=false pour tous les devices
                                         (cleanup apres kill abrupt qui skip le finally
                                          de handleDeviceConnection)
5. Compte admin auto-genere si count==0 (password 16 chars SecureRandom)
6. configureAuth()                   <- JWT HMAC256
7. startDeviceRelay(tcpPort)         <- TCP relay dans coroutine IO
8. configureAppRelay()               <- WebSocket /ws/app
9. launch: flush history buffer (5s)
10. launch: cleanup history >24h (1h)
11. routing: staticResources + API + admin

Gestion port occupe au demarrage

Si le port est deja utilise, le serveur affiche un message clair et s'arrete proprement : 
FAILED TO START — Port 8080 is already in use
To fix, edit the port in: ~/.instantiot/server.properties
  http.port=8081    (or any free port)
Then restart the server.

6. Authentification et securite

JWT

ParametreValeur
AlgorithmeHMAC256
Expiration30 jours
Issuerinstantiot-server (hardcode dans configureAuth.kt)
Audienceinstantiot-app
SubjectuserId (UUID)
Secret~/.instantiot/secret.key (chmod 600)
Validation JWT : a chaque requete, le serveur verifie que le user existe encore en DB via userRepository.findById(userId). Un user supprime ne peut plus utiliser son token.

Passwords

  • Hashing : BCrypt avec salt automatique
  • Validation : username 3-32 chars [a-zA-Z0-9_], password 8-128 chars
  • Admin : 16 chars via java.security.SecureRandom, affiche une seule fois dans les logs
  • Premier login : password_changed=false -> le dashboard force le changement

Tokens device

  • UUID v4 genere a la creation
  • Retourne en clair une seule fois dans la reponse POST
  • Seul le SHA-256 est stocke en DB
  • Verification TCP : SHA-256(token_recu) == token_hash_db

Rate limiting

ScopeLimiteCleRoutes
auth10 req / minuteIP distante/api/login, /api/register

Ownership isolation

Pattern applique partout :

val resource = repository.findById(id)
if (resource == null || resource.ownerId != userId) {
    respond(404)  // ne revele pas l'existence
}

Applique sur : toutes les routes REST, handshake WebSocket, relay per-frame (in-memory).

Verification port disponible

Avant de sauvegarder un nouveau port, le serveur tente un ServerSocket.bind() avec reuseAddress=false sur 0.0.0.0 et 127.0.0.1. Si le port est occupe -> 409 Conflict.

8. Relay temps reel — TCP et WebSocket

DeviceRelay — TCP (port configurable, defaut 9001)

Fichier : relay/DeviceRelay.kt

1. ESP ouvre connexion TCP
2. Handshake : [PAYLOAD_LEN(1B) | PAYLOAD_BYTES]
   payload = "token"              (legacy, pas d'annonce de heartbeat)
   payload = "token:heartbeatMs"  (nouveau, lib Arduino avec Instant.setHeartbeat(ms))
3. Server SHA-256(token) -> lookup DeviceTable
4. Authentifie -> session dans SessionRegistry, device online
   soTimeout ajuste selon heartbeatMs :
     - heartbeatMs declare -> soTimeout = heartbeatMs * 2.5 (clamp 2s..120s)
     - legacy              -> soTimeout = 90s
5. Boucle : trame binaire iWidgets v1
   a. TYPE = 0xFE (heartbeat) -> skip dispatch, la reception reset le soTimeout
   b. sinon extractWidgetId + extractPayload
   c. lastPayloads[widgetId] = payload (RAM, sub-ms)
   d. historyBuffer.add(entry) (flush 5s)
   e. widgetRepository.updateLastPayload (async IO)
   f. broadcast trame aux apps du projet (WebSocket)
6. Deconnexion (socket close / soTimeout / exception)
   -> finally : updateOnlineStatus(false), unregisterDevice
   -> broadcast device_offline (reason=disconnected)
Protections TCP : keepalive, soTimeout adaptatif (= heartbeat x 2.5), HANDSHAKE_TIMEOUT_MS = 10s pre-handshake, body max 1024 bytes, CRC8 verifie.

Heartbeat (detection offline rapide)

La lib Arduino InstantIoT envoie toutes les heartbeatMs (defaut 5000 ms) une trame dediee TYPE=0xFE (DEV_COUNT=0 | WID_LEN=0 | TYPE=0xFE | EVENT=0 | CRC). Le serveur la valide (CRC/sync) mais ne dispatch rien aux apps et ne persiste pas : la simple reception d'un byte reset le soTimeout OS-level.

Si aucune trame (widget OU heartbeat) n'arrive dans la fenetre heartbeatMs x 2.5, la SocketTimeoutException propagee declenche le finally -> updateOnlineStatus(false) + broadcast device_offline aux apps connectees au projet. Detection typique avec heartbeat=5s : ~12.5s max apres unplug / Wi-Fi drop / ESP crash.

Cote API Arduino : Instant.setHeartbeat(uint32_t ms) dans le setup() (avant begin()). La facade InstantIoTWiFiServer force a la fois l'annonce au handshake (transport) et l'emission periodique via loop() (couche core). Mettre 0 desactive le heartbeat (mode legacy, serveur 90s).

AppRelay — WebSocket /ws/app

Fichier : relay/AppRelay.kt

1. JWT verifie dans le header Authorization
2. Handshake : premier message texte = projectId
3. Ownership verifie : projectRepository.findById(projectId).ownerId == userId
4. Session enregistree (multi-session supporte)
5. Boucle : trames binaires (commandes)
   a. extractDeviceIds(frame) -> IDs cibles
   b. Ownership per-frame : deviceSession.device.ownerId == userId (in-memory)
   c. trimDeviceHeader(frame) -> DEV_COUNT=0
   d. relay TCP vers devices cibles (via DeviceOutbox serialise + backpressure)
   e. Si echec (offline / forbidden / I/O error) -> envoi Frame.Text command_failed a la session
6. Deconnexion -> session specifique retiree
Protections WebSocket : JWT, ownership projet (DB), ownership device per-frame (in-memory), maxFrameSize 8 KB, ping/pong 15s, timeout 30s.

Control events WebSocket

Fichiers : relay/ControlEvent.kt, relay/ControlEventBroadcaster.kt

Le WebSocket /ws/app multiplexe deux couches apres le handshake :

  • Frame.Binary → trames iWidgets v1 (data temps reel, devices ↔ apps)
  • Frame.Text → control events JSON (etat des devices, erreurs de commande)

L'app discrimine sur le type de frame pour router vers le parser binaire ou le parser JSON.

Types d'events

typeDirectionPayloadDeclencheur
device_online Server → toutes les apps du projet {type, deviceId, deviceName} Device ESP authentifie et registre dans SessionRegistry (DeviceRelay ligne apres registerDevice)
device_offline Server → toutes les apps du projet {type, deviceId, reason}
  • reason=disconnected → TCP close / soTimeout (finally de handleDeviceConnection).
    soTimeout = heartbeatMs x 2.5 (legacy: 90s). Detection sous ~12.5s avec heartbeat 5s.
  • reason=token_renewed → admin a appele POST /api/devices/{id}/renew-token
  • reason=deleted → admin a appele DELETE /api/devices/{id}
command_failed Server → session emettrice uniquement {type, deviceId, reason}
  • reason=device_offline → session TCP absente ou socket ferme
  • reason=forbidden → device appartient a un autre user
  • reason=relay_error → exception lors de l'ecriture TCP vers le device

Flux device online/offline

ESP se connecte TCP  → handshake token OK  → registerDevice
                                            → ControlEventBroadcaster.deviceOnline(projectId, deviceId, deviceName)
                                            → Frame.Text broadcast a toutes les apps du projet

ESP disconnect TCP   → finally unregisterDevice
                     → updateOnlineStatus(false)
                     → ControlEventBroadcaster.deviceOffline(projectId, deviceId, "disconnected")

POST renew-token     → ControlEventBroadcaster.deviceOffline(..., "token_renewed")  (broadcast AVANT close)
                     → socket.close()  → handler TCP finally re-broadcast "disconnected" (double event accepte)

DELETE device        → ControlEventBroadcaster.deviceOffline(..., "deleted")        (broadcast AVANT close)
                     → socket.close()  → handler TCP finally re-broadcast "disconnected"

Flux command_failed (App → Device en echec)

App envoie trame binaire (DEV_COUNT ≥ 1) sur WS
  → relayFrameToDevices(session, userId, frameBytes)
  → pour chaque targetDeviceId :
      - deviceSessions[targetDeviceId] absent/socket closed
          → commandFailed(session, deviceId, "device_offline") sur la session emettrice
      - deviceSession.device.ownerId != userId
          → commandFailed(session, deviceId, "forbidden")
      - outbox ferme / exception lors de l'ecriture TCP
          → unregisterDevice + commandFailed(session, deviceId, "relay_error")
Contrat app : a la reception d'un command_failed, l'app affiche un toast contextuel ("Device hors ligne", etc.). Pas de correlation fine par commande — les echecs restent rares et l'user voit simplement l'action qui n'a pas eu d'effet (LED qui ne s'allume pas, etc.).

9. Protocole binaire iWidgets v1

Fichier : relay/FrameParser.kt

Format de trame

+------+-----+----------+-----------+---------------------+---------------------------------+------+
| 0xAA | VER | LEN (2B) | DEV_COUNT | [DEV_LEN|DEV_ID]*N | WID_LEN|WID|TYPE|EVENT|PAYLOAD  | CRC8 |
|  1B  | 1B  |  LE      |    1B     |    variable         |           variable              |  1B  |
+------+-----+----------+-----------+---------------------+---------------------------------+------+

Pas de numero de sequence : tous les transports supportes (TCP/WebSocket/BT RFCOMM/BT BLE/Serial) garantissent un ordonnancement fiable sans duplication. Un SEQ applicatif ne couvrirait aucun scenario reel et causait des drops silencieux apres redemarrage de l'app ou du device.

ChampTailleDescription
0xAA1BSync byte
VER1B0x01
LEN2B LETaille du body (max 1024)
DEV_COUNT1B0 = device->app, N = app->devices
DEV_LEN|DEV_IDvarUUID device cible (repete N fois)
WID_LEN|WIDvarUUID du widget
TYPE1BType. Le serveur ne l'interprete pas, sauf 0xFE (heartbeat) qu'il intercepte pour reset le soTimeout sans dispatcher.
EVENT1BEvenement (serveur ne l'interprete pas)
PAYLOADvarDonnees opaques (stockees base64)
CRC81BCRC-8/SMBUS (poly 0x07) sur le body

Methodes FrameParser

MethodeDirectionDescription
isValid(frame)Les deuxSync + version + taille + CRC8
extractType(frame)Device->ServerByte TYPE. Utilise par DeviceRelay pour detecter les heartbeats (0xFE) et skip le dispatch applicatif.
isStreamingCommand(frame)App->ServerClassifie la trame comme streaming (slider ValueChanging, joystick PositionChanged) pour la backpressure outbox.
extractWidgetId(frame)Device->ServerUUID widget de la trame
extractPayload(frame)Device->ServerBytes opaques (stockes base64)
extractDeviceIds(frame)App->ServerUUIDs devices cibles
trimDeviceHeader(frame)App->DeviceRetire DEV_COUNT, recalcule LEN+CRC
hashDeviceToken(token)-SHA-256 pour lookup DB

10. Sessions et concurrence

Fichier : relay/SessionRegistry.kt — objet singleton, tout en memoire.

StructureTypeUsage
appSessionsConcurrentHashMap<UserId, CopyOnWriteArrayList<AppSession>>Multi-session par user (phone + tablet)

Modele de concurrence

  • 1 coroutine Dispatchers.IO par device TCP
  • 1 coroutine Ktor par WebSocket app
  • 1 coroutine background flush history (5s)
  • 1 coroutine background cleanup history (1h)
  • Frame parsing sur Dispatchers.Default (CPU-bound)

11. History buffer et flush

Device envoie trame
       |
       v

       v

Design : la DB n'est jamais dans le chemin critique du relay. Le batch insert est ~5x plus rapide que N inserts individuels.

15. Systeme de licence

Principe

Chaque licence est un JWT signe avec RSA-256. La cle privee reste chez InstantIoT (pour generer les licences). La cle publique est embarquee dans le JAR (pour verifier). Impossible a forger sans la cle privee.

Contenu du JWT licence

{
  "sub": "INST-A7K2-M9X1-P3B8",   // identifiant licence unique
  "plan": "beta",                   // plan: beta, pro, enterprise
  "iss": "instantiot.io",           // issuer verifie
  "iat": 1713150000,                // date de creation
  "exp": 1798761600                 // date d'expiration
}

Flow

  1. Le client achete une licence → recoit un JWT signe par email
  2. Premier lancement du serveur → le dashboard affiche "Enter your licence key"
  3. Le client colle le JWT → le serveur verifie la signature RSA avec la cle publique
  4. Si valide → stocke dans ~/.instantiot/licence.key
  5. Aux prochains demarrages → lit le fichier, re-verifie signature + expiration
  6. Si invalide/expire → redemande la licence
Securite : aucun appel reseau necessaire. Tout se fait en local. Meme si le client decompile le JAR, il ne peut que lire la cle publique — pas forger de licence. La verification fonctionne 100% offline.

Fichiers
